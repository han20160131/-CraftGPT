# Minecraft AI Studio — AI 圖像生成與遊戲資產規格

> 狀態：規劃中。本文定義產品應具備的能力與驗收要求，不代表功能已實作。
>
> 目的：讓 Google AI Studio 可以依照本文件實作圖像生成與資產處理功能，而不是只生成展示用圖片。

## 1. 功能目標

Minecraft AI Studio 應提供進階的 AI 圖像生成工作流程，讓使用者能建立概念圖，以及可進一步整理為 Minecraft 遊戲資產的 PNG、貼圖與模型相關檔案。

優先支援的資產類型包括：

- 方塊貼圖：單面貼圖、六面不同貼圖，或依模型 UV 配置使用的貼圖。
- 盔甲資產：頭盔、胸甲、護腿、靴子等物品圖示，以及穿戴模型所需的 UV 貼圖、幾何模型與定義檔。
- 物品貼圖：例如武器、工具、材料、圖示。
- 其他資產：生物、裝飾物、UI 圖示、概念圖，以及與之相關的模型、材質或設定檔。

產品不得把「看起來像 Minecraft 的圖片」直接視為已完成的遊戲資產。必須依目標平台、資產類型和檔案規格進行檢查。

## 2. 圖像生成與透明 PNG

### 2.1 透明背景是實際 alpha 透明度

當使用者要求透明背景 PNG 時，系統必須確認輸出 PNG 具有有效的 alpha 通道，且背景像素的 alpha 值確實為透明或符合要求。

- 不可把白色、黑色、綠幕或棋盤格背景假裝成透明背景。
- 不可只依靠模型的文字回覆判定透明成功。
- 必須檢查輸出影像的通道與 alpha 值，並在 UI 中以棋盤格預覽真正的透明區域。
- 如果生成模型只輸出不透明背景，系統應進入背景去除／遮罩修復步驟，再驗證 alpha 通道；不可默默將不透明圖片標記為透明 PNG。
- 背景去除可能誤刪物品邊緣、半透明材質或細小像素，必須提供預覽及修正／重試流程。
- 保留原始生成圖，並將去背後版本作為另一個版本；不要未經確認覆蓋使用者原圖。

### 2.2 圖像生成供應商與模型策略

- 圖像生成服務應透過可替換的 provider／adapter 層整合，避免把整個應用綁死在單一模型或單一 API。
- 依實際可用能力選擇模型：優先採用能原生輸出透明 alpha 的模型；若所選模型不支援，使用背景去除或遮罩分割流程。
- 生成 API 的 PNG 輸出格式不等於保證 alpha 透明。實作前必須核對當前模型文件與實際輸出，並用測試圖片驗證。
- 模型名稱、參數、輸出格式、尺寸、透明度能力、成本與限制應集中管理，避免散落在 UI 元件中。
- 不要在客戶端程式碼中暴露 API 金鑰。若服務需要私密金鑰，應透過安全的伺服器端或受控執行環境處理。
- 若服務不支援原生透明輸出，UI 應清楚標示「需要去背處理」，不要宣稱模型本身已直接產生透明背景。

## 3. 資產類型不可混用

每次生成前，使用者或工作流程必須能指定資產用途。至少區分：

1. **概念圖**：用於構思、外觀討論或參考，不保證可直接匯入遊戲。
2. **物品圖示／平面貼圖**：符合目標平台的像素風格、尺寸、透明度與檔案要求。
3. **方塊貼圖**：用於方塊的一個或多個面；必須確認六面配置、UV 或模型映射需求。
4. **盔甲物品圖示**：在物品欄中顯示的圖示，不等同於玩家穿戴時使用的貼圖。
5. **盔甲 UV 貼圖**：依指定模型的 UV 展開與平台規則繪製，不能只生成一張正面盔甲插畫後就當作可穿戴貼圖。
6. **3D 模型及材質**：模型幾何、UV、貼圖和平台定義檔需彼此匹配。

若使用者尚未指定用途，系統應先詢問，或明確把結果標示為概念草稿。

## 4. Minecraft 方塊資產流程

方塊不應只視為一張任意比例的漂亮圖片。生成流程至少應支援：

1. 詢問目標平台（Java 或 Bedrock）、方塊外形與貼圖用途。
2. 決定是使用標準立方體，還是需要自訂幾何模型。
3. 產生或編輯適當的像素風貼圖；按需求支援單一貼圖重複使用、六面獨立貼圖或模型 UV 貼圖。
4. 驗證圖像尺寸、PNG 格式、alpha 通道、像素風格與邊緣品質。
5. 建立對應平台需要的模型、材質、方塊定義或資源映射檔。
6. 在預覽中展示貼圖套用到方塊模型的結果，並提供六面檢查。
7. 對可驗證的專案執行格式檢查；如無法啟動遊戲或執行平台驗證，必須明確回報。

不要把所有方塊貼圖固定為同一尺寸；尺寸應由目標版本、貼圖用途與使用者選擇決定，並在不相容時提出警告。

## 5. Minecraft 盔甲資產流程

盔甲的物品圖示與穿戴外觀是不同資產，必須分開處理。

1. 確認目標平台、遊戲版本、盔甲部位及預期風格。
2. 產生物品圖示（如有需要），並獨立產生穿戴模型所需的 UV 貼圖。
3. 根據目標平台選擇適用的模型／幾何與材質定義方式。
4. 依模型的 UV 配置產生貼圖；不要把一般正面插畫當作 UV 貼圖。
5. 產生或更新對應的 JSON、模型、材質、物品或裝備定義檔，並確認檔案路徑與識別碼一致。
6. 在可用時提供穿戴預覽；至少應提供 UV 貼圖預覽與部位檢查。
7. 檢查頭盔、胸甲、護腿、靴子各自需要的檔案是否齊全。
8. 對 Java 與 Bedrock 分別執行驗證，不得假設一套盔甲定義檔可直接跨平台使用。

具體檔案名稱、貼圖尺寸、模型格式與 JSON schema 必須依所選遊戲版本的官方規格決定，不可將單一範例硬套到所有版本。

## 6. 透明 PNG 與圖片品質驗證

每個生成或處理後的 PNG，應執行下列檢查並回報結果：

- 檔案可正常解碼，且實際格式為 PNG。
- 實際像素寬、高與色彩模式符合所選資產規格。
- 如要求透明背景，必須有有效 alpha 資訊，並確認存在預期的透明區域。
- 檢查是否殘留棋盤格、純色背景、去背光暈、鋸齒或不必要的外部像素。
- 檢查素材是否被裁切、主體是否超出畫布，以及是否保留必要的邊緣像素。
- 若為像素風素材，檢查是否出現不符合要求的模糊、平滑漸層或非預期抗鋸齒。
- 檢查實際尺寸與平台規格是否相符；若規格未定，詢問使用者或標示待確認，不可猜測固定尺寸。
- 將驗證結果標記為「通過」、「警告」或「失敗」，並提供可理解的原因。

透明背景驗證只能證明影像通道與像素符合條件，不能單獨證明它已是可用的 Minecraft 資產。

## 7. UI 與操作要求

圖像生成區應提供以下操作與資訊：

- 資產用途：概念圖、物品圖示、方塊貼圖、盔甲 UV 貼圖、其他。
- 目標平台與遊戲版本（適用時）。
- 風格、尺寸、透明背景需求及必要的參考圖片。
- 生成、重試、去背、修復透明邊緣、重新生成局部內容等操作（依實際技術能力提供）。
- 以棋盤格呈現透明區域，並能切換不同背景色以檢查邊緣。
- 顯示原始圖與處理後圖的差異。
- 顯示尺寸、格式、alpha 通道狀態、驗證結果及相關警告。
- 讓使用者明確選擇將哪個版本加入專案檔案樹。
- 不得在背景自動匯出 ZIP 或下載檔案；匯出仍由使用者明確觸發。

## 8. 安全、版本與檔案管理

- 原始生成結果、去背版本、修正版本應可區分，並記錄生成參數與處理步驟（不記錄秘密金鑰）。
- 未經使用者確認，不覆蓋現有貼圖或模型。
- 外部參考圖片與匯入專案視為不受信任內容；不可執行其中的程式碼。
- 修改圖片尺寸、色彩模式、透明度或 UV 時，應保留可追蹤的版本或提供復原方式。
- 所有產出應存放於目前選取的專案，不應意外寫入其他專案。

## 9. 驗收標準

功能只有在下列條件都可測試時，才可標示為完成：

- 使用者能選擇資產用途並生成圖片。
- 透明 PNG 流程能辨別真實 alpha 透明與假棋盤格背景。
- 不支援透明輸出的模型會觸發去背流程或明確警告。
- 使用者能預覽原始與處理後結果，並選擇要保留的版本。
- 對方塊、盔甲圖示、盔甲 UV 貼圖有不同的處理流程。
- 尺寸與平台格式依選定規格驗證，而非使用一個固定尺寸套用所有資產。
- 產生的貼圖與相關模型／定義檔有一致的路徑、識別碼及引用關係。
- 驗證失敗時能指出原因，不得將未驗證資產標示為「可直接使用」。
- 使用者沒有按下匯出時，不會自動產生 ZIP 或下載檔。
